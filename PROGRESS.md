## 06.11.2026 — Заказы, API и кабинет

Работа продолжается в `feature/orders-module`, от `feature/reports-module` (`49d22ed`).

**Сделано**

- Модели `CustomerOrder`, `OrderItem`, `OrderPayment`, `OrderEvent`, миграция `20261106090000_customer_orders`. Черновики, подтверждение, готовность, выдача и отмена. Клиент, магазин, доставка с адресом и телефоном либо самовывоз, комментарий и история сотрудника.
- API `/stores/:storeId/orders`. Редактирование черновика проверяет версию. Подтверждение атомарно резервирует свободный остаток через `Stock.reservedQuantity`. Повторное подтверждение сохраняет один резерв. Одновременные заказы конкурируют в Serializable-транзакциях.
- Частичные денежные предоплаты с уникальным идентификатором операции, ограничение суммой заказа, статусы «не оплачен / частично оплачен / оплачен». Наличная предоплата проводится внесением в открытую смену, карточная учитывается отдельной записью заказа. Бонусы и долг для предоплаты исключены.
- Выдача полностью оплаченного заказа создаёт обычный чек через общую транзакционную реализацию продаж. Фиксируются цены и автоматические скидки сохранённого заказа. Уже принятые наличные повторно не вносятся. Резерв, списание товара, чек, бонусы клиента и вознаграждение сотрудника сохраняются атомарно. Выдача выполняется в собственной открытой смене сотрудника.
- Отмена невыданного заказа освобождает резерв и возвращает всю предоплату исходными способами. При нехватке наличных весь запрос откатывается, включая снятие резерва. Повторная отмена не дублирует возврат. Возвраты выданного заказа оформляются по созданному чеку через существующий экран продаж, ссылка открывает нужные магазин и чек. Возвраты видны в карточке заказа.
- Экран `/orders`, поиск и статусы, редактор с поиском товара и клиента, предоплата, выдача, подтверждение отмены, оплаты и история. Новые права `orders.view/create/edit/confirm/pay/fulfill/cancel`, серверная проверка магазина и дополнительных прав кассы/продаж. Seed добавляет права стандартным неизменённым ролям. Для ролей с вручную настроенными правами новые разрешения назначаются явно.
- Финансовый журнал учитывает поступления и возвраты предоплаты по фактической дате. Оплата созданного из заказа чека повторно в журнал не добавляется. Выручка возникает при выдаче.
- При повторном прогоне отчётов на PostgreSQL с `TimeZone=Asia/Tashkent` исправлено сравнение UTC timestamp-полей с границами периода. До исправления расход с датой в полночь выпадал из отчётов прибыли и финансов. Доступ к `/reports` в кабинете согласован с `reports.view`.

**Проверки**

- На Windows с обычным Prisma engine прошли `typecheck`, `lint`, тесты API и кабинета, сборки API и Next.js, проверка кодировки. Общий прогон затронутых пакетов через Turbo завершил 20 задач. После изменения SQL выполнен повторный интеграционный прогон.
- На отдельном PostgreSQL 16 с SCRAM-паролем, localhost и новой временной директорией применены все миграции и seed. `tools/verify-orders-real-db.mjs` проверил HTTP-вход, черновики, версии, доставку, конкурентные резервы, частичные оплаты и их повторы, запрет переплаты и оплаты бонусами, неизменность цены после изменения каталога, выдачу без повторного прихода наличных, начисление сотруднику, возврат чека, отмену с возвратом и повтором, откат при нехватке денег, чужие магазины и роли без права записи, финансовый журнал.
- Повторно прошли `tools/verify-reports-real-db.mjs` (18/18) и `tools/verify-real-db-mvp.mjs` на этом изолированном стенде.
- Браузерный прогон нового экрана ограничен. Автоматическая проверка отклонила запуск тестового Next.js-сервера с сообщением `blocked by policy`. Сборка, проверки типов и HTTP-проверки выполнены. Визуальное поведение нового экрана в браузере требует отдельной проверки.

**Принятые правила и следующий шаг**

- Подтверждение требует достаточного свободного остатка. Выдача требует полной оплаты, положительной суммы заказа и собственной открытой смены. Цена фиксируется при сохранении черновика. Возврат по карте оператор проводит на терминале и подтверждает в программе.
- Для будущей выкладки нужны миграция, seed, пересборка API и кабинета. Работа сохранена в отдельной feature-ветке.
- Далее по HANDOFF идут денежные счета и переводы, календарь дашборда Душанбе, оставшиеся товарные функции, дельта-синхронизация и 200 чеков через Windows EXE.

## 06.11.2026 — «Создать документ» как в CloudShop

- Формы CloudShop сняты без сохранения: Закупка, Оприходование, Списание, Возврат закупки, Приход, Расход — общий вид «товары слева, лист документа справа» (кнопка «Сохранить», дата, «Документ проведён», «<Тип> #», контрагент и магазин, «← Выберите товары»).
- `/documents/new?kind=…`: **Закупка** (поставщик, номер, цены закупки, «Документ проведён» — сразу оприходовать, вкладка «Оплата»), **Оприходование** и **Списание** (несколько строк одним документом, обязательное основание), **Приход** (наличные в кассу открытой смены, категория платежа), **Расход** (касса смены или расчётный счёт, категория, дата).
- API: `POST /stores/:storeId/stock/write-off-documents` и `…/receive-documents` — все строки в одной транзакции, общий источник = `operationId`, повтор с теми же строками возвращает сохранённый документ, с другими — 409, нехватка остатка по одной строке откатывает весь документ. В журнале документов появился тип «Оприходование».
- Меню «Создать документ» в порядке CloudShop: Продажа, Закупка, Возврат продажи, Инвентаризация, Оприходование, Списание, Перемещение, Приход, Расход, Товар.

**Проверки:** typecheck, lint, 190 автотестов, `check:text`, `next build`; `tools/verify-create-documents-real-db.mjs` на отдельной PostgreSQL 4/4; через интерфейс в Chromium созданы оприходование (2 строки), списание (2 строки, один документ) и приход — документы сразу видны в журналах.

**Не сделано:** «Возврат закупки» (в API нет возврата поставщику), «Перевод» денег между счетами (нет модели счетов) — пункты не добавлены, чтобы не было пустых кнопок.
