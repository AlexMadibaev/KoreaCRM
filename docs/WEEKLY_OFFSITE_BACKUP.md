# Еженедельная копия с локального ПК на VPS

На исходном Windows ПК рабочие данные кабинета находятся в PostgreSQL, фотографии товаров — в `.mvp-local/product-images`, локальный кеш и очередь кассы — в `%APPDATA%/com.koreacrm.pos/pos-cache.sqlite3`. Касса отправляет продажи в API при доступной связи. Еженедельная задача создаёт **архив для восстановления**, а не синхронизирует рабочую базу VPS.

`tools/weekly-offsite-backup.ps1` каждое воскресенье в 23:00 по времени ПК:

1. Создаёт `pg_dump` и проверяет его через `pg_restore --list`.
2. Архивирует фотографии и делает согласованный снимок SQLite через Python `sqlite3.backup` с проверкой целостности.
3. Записывает SHA-256 каждого файла в `manifest.json`.
4. Если VPS настроен, передаёт файлы по SSH/SCP и сверяет контрольные суммы на VPS. Только после этого удаляет **созданный архив** с ПК. При ошибке связи или проверки архив остаётся в `.mvp-local/backups/weekly-pending` и повторно отправляется при следующем запуске.

Рабочие PostgreSQL, фотографии и SQLite **не удаляются**: без них локальная программа перестанет работать, а непринятые продажи могут пропасть. Очередь кассы очищать вручную нельзя. Пока VPS не настроен, все еженедельные архивы остаются на ПК; следите за свободным местом.

## Включение на исходном ПК

Нужны PostgreSQL 16 client tools в `C:\Program Files\PostgreSQL\16\bin`, Python 3 при наличии локальной кассы и встроенный Windows OpenSSH Client. Сначала сделайте пробную локальную копию:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\tools\weekly-offsite-backup.ps1 -LocalOnly
```

После успешной проверки установите задачу Windows:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\tools\install-weekly-offsite-backup.ps1
```

Задача работает в учётной записи текущего пользователя, когда он вошёл в Windows. Пропущенный запуск выполняется после следующего входа. Результат смотрите в Планировщике заданий под именем `KoreaCRM-WeeklyOffsiteBackup` и в `.mvp-local/backups/weekly-pending`.

В личном кабинете владельца на **локальном Windows MVP** есть блок «Резервные копии» и кнопка «Создать копию сейчас»; после настройки VPS она станет «Создать и отправить». Кнопка запускает тот же скрипт, что и расписание. Доступ разрешён только роли `OWNER`, по действующему токену входа, при локальном запуске через `tools/start-mvp.ps1`. На VPS этот маршрут отключён. Повторное одновременное копирование блокируется.

## Подключение VPS

На VPS нужен отдельный SSH-пользователь с записью в каталог резервных копий, доступный только ему и администратору. Настройте вход по ключу и один раз проверьте SSH-подключение с ПК, чтобы закрепить ключ хоста. В `.mvp-local/weekly-offsite.json` создайте файл:

```json
{
  "sshTarget": "backup@example.com",
  "remoteDirectory": "/srv/koreacrm-backups",
  "sshKeyPath": "C:\\Users\\USERNAME\\.ssh\\koreacrm_backup"
}
```

`sshKeyPath` можно опустить, если ключ уже выбирается SSH автоматически. Скрипт использует `BatchMode=yes` и `StrictHostKeyChecking=yes`; при неподготовленном ключе или неизвестном хосте загрузка завершится ошибкой с сохранением локального архива. Для ручной проверки после настройки запустите `weekly-offsite-backup.ps1` без `-LocalOnly`. SSH-пароли и ключи не помещайте в репозиторий.

## Восстановление

Скопируйте каталог `weekly-...` с VPS на отдельный компьютер и сравните SHA-256 файлов с `manifest.json`. Создайте **новую пустую** PostgreSQL базу и восстановите `database.dump` через `pg_restore --exit-on-error --single-transaction --no-owner --no-acl`. Распакуйте `product-images.zip` в родительский каталог изображений нового API: внутри ZIP уже есть папка `product-images`. `pos-cache.sqlite3` предназначен для восстановления кассы на отдельной Windows установке; перед заменой остановите кассу. Не накатывайте архив поверх действующей базы или SQLite.

Перед использованием с реальными данными проверьте полное восстановление на отдельной базе и доступ к фотографиям и чекам. Архивы на VPS содержат персональные данные и локальные сведения кассы, поэтому ограничьте права каталога и настройте отдельное копирование с VPS на другой носитель.

## Задача для следующего ИИ-агента

Состояние на 25.10.2026: задача Windows `KoreaCRM-WeeklyOffsiteBackup` установлена и ожидает воскресенья 23:00; локальный пробный архив успешно создан и проверен. VPS-подключение ещё не задано, потому что пользователь пришлёт реквизиты позже. **Не используйте** `.mvp-local/mvp.env` как источник секретов VPS и не публикуйте содержимое `.mvp-local`.

Когда пользователь даст IP/домен и SSH-пользователя:

1. Проверьте, что на VPS создан отдельный каталог для архивов с правами только у SSH-пользователя. Не кладите архивы в публичный каталог сайта или GitHub. Потребуются `ssh`, `scp` на ПК и `sha256sum` на VPS.
2. Настройте на ПК SSH-ключ для этого пользователя и вручную проверьте отпечаток ключа VPS, затем тестовый `ssh user@host`. Скрипт не подтверждает неизвестные ключи хостов автоматически.
3. Создайте `.mvp-local/weekly-offsite.json` по примеру выше с реальными `sshTarget`, `remoteDirectory`, `sshKeyPath`. Права на файл и закрытый ключ ограничьте текущим пользователем Windows. Не меняйте рабочий `DATABASE_URL` или адрес API кассы ради копирования.
4. Запустите `powershell -NoProfile -ExecutionPolicy Bypass -File .\tools\weekly-offsite-backup.ps1` из `D:\KoreaCRM`. Скрипт создаст новый архив и отправит его вместе с ранее накопленными `weekly-pending`. Убедитесь, что он сообщил `Server verified; local archive removed` для каждого каталога.
5. На VPS проверьте число каталогов `weekly-*`, файлы `database.dump`, `manifest.json`, `product-images.zip` и, если касса установлена на ПК, `pos-cache.sqlite3`. Сверьте SHA-256 с манифестом. Проверьте, что `weekly-pending` на ПК пуст, а рабочие PostgreSQL, фотографии и SQLite продолжают работать.
6. Восстановите один архив на **отдельной** тестовой базе и проверьте вход, товары, фотографии, остатки и чек. Только после этого считайте VPS-передачу готовой.
7. Проверьте в Планировщике заданий следующий запуск и результат ручного запуска задачи под тем же Windows-пользователем. Если ПК был выключен в воскресенье, включён `StartWhenAvailable`, но запуск произойдёт только после входа пользователя.

Если SSH-загрузка или сверка завершилась ошибкой, локальные архивы остаются в `weekly-pending`. Не удаляйте их вручную и не очищайте локальную SQLite ради освобождения места. Проверьте SSH-доступ, свободное место на VPS и повторите запуск. Настройте отдельное хранение копий **самого VPS** и срок их удержания: текущий скрипт сохраняет все проверенные копии на сервере и не удаляет их автоматически.
