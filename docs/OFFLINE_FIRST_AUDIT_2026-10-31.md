# Offline-first POS: аудит 31.10.2026

Источник требований: ТЗ «Korea CRM — Offline-First POS, синхронизация и резервное копирование» от 31.10.2026. Этот документ фиксирует состояние кода, а не обещает готовность к эксплуатации двух автономных точек.

## Уже реализовано

- Windows POS использует SQLite (`apps/pos/src-tauri/src/local_cache.rs`) для копии товаров, цен, остатков своего магазина и клиентов. Снимок заменяется в одной транзакции; данные разделены по пользователю и магазину.
- Локальный вход подготовленного кассира действует семь дней (`offline_session.rs`), очередь продаж переживает перезапуск (`sync_queue.rs`). Продажа получает `operationId`; API проверяет повторную отправку в транзакции (`apps/api/src/sales/sales.service.ts`).
- После оформления чек сначала ставится в локальную очередь, затем отправляется. При восстановлении связи касса повторно входит, отправляет очередь и показывает конфликты. Неподтверждённые продажи учитываются при показе доступного остатка.
- Сервер хранит продажи и движения склада в PostgreSQL. Остатки разделены по магазинам. Есть отдельные операции перемещений.
- Существует ручной и еженедельный архив PostgreSQL, фотографий и SQLite (`tools/weekly-offsite-backup.ps1`, `docs/WEEKLY_OFFSITE_BACKUP.md`). Передача на отдельное хранилище требует настройки SSH.
- В этом этапе SQLite переключена на WAL, `synchronous=FULL`, ожидание блокировки до пяти секунд. Экран отправки продаж показывает результат `quick_check` локальной базы.

## Работает частично

- Касса загружает каталог, цены, остатки и клиентов целиком через постраничный API. Это атомарный снимок на устройстве, но **не инкрементальная двусторонняя синхронизация**. После первого подключения обновление происходит при входе или вручную; серверные изменения не приходят автоматически по курсору.
- Онлайн-поиск обращается к API и переходит на SQLite при ошибке сети. Локальные данные должны быть успешно подготовлены заранее. Нельзя считать отсутствие `navigator.onLine` достаточной проверкой сервера.
- Очередь поддерживает повтор и видимый конфликт, однако экспоненциальной задержки и серверного журнала синхронизации пока нет.
- Офлайн доступны продажи с ранее сохранёнными клиентами и открытой кассовой сменой. Создание нового клиента, открытие смены, возврат и изменение персональной скидки требуют связи.
- На сервере идемпотентность продаж обеспечена `operationId`, но в модели продажи нет отдельного времени создания на кассе и времени получения сервером.
- Архив SQLite согласованно создаётся через SQLite backup API; еженедельная задача сама по себе не заменяет ежедневные зашифрованные копии PostgreSQL и проверку восстановления.

## Отсутствует или требует исправления

1. Серверный журнал изменений с курсором, версиями и фильтрацией по магазину; постраничная выдача дельт товаров, цен, остатков, клиентов и прав.
2. Применение полученных дельт в SQLite в одной транзакции с курсором. Нужен механизм безопасной повторной полной загрузки после потери курсора.
3. Локальные заказы со статусами «Оплачен» / «Не оплачен» и последующей сменой статуса. Не расширять текущую модель оплаты без согласованного правила переходов.
4. Автоматическая сверка складских движений после офлайн-продаж, аудит отрицательных остатков и отдельные подтверждения перемещений.
5. Полный центр синхронизации: последняя ошибка, журнал попыток, состояние каждой операции и явное восстановление после исправления конфликта.
6. Локальная резервная копия на **каждом** кассовом ПК и проверенный сценарий восстановления нового устройства. Текущий архивный скрипт привязан к конкретной установке проекта.
7. Политика серверных копий: ежедневные/еженедельные/ежемесячные сроки, шифрование, отдельное хранилище и регулярное пробное восстановление. WAL-архивирование PostgreSQL оценить отдельно по допустимой потере данных.
8. Проверки двух устройств и двух магазинов, длительного отключения, потери ответа после записи, повреждения SQLite, восстановления PostgreSQL и тест реального Windows EXE.

## Порядок следующих изменений

1. Определить контракт синхронизации и миграцию серверного журнала. Сначала включить запись изменений для каталога, цен, склада, клиентов и скидок; затем выдать дельты по курсору с проверкой роли и магазина.
2. Добавить локальный курсор и транзакционное применение дельт в SQLite. Полную загрузку оставить для регистрации кассы и восстановления.
3. Отделить локальную операцию продажи от отправки, расширить статусы заказов и отладить конфликты склада. Для каждого изменения сохранить автора, магазин, устройство и время.
4. Завершить резервирование и восстановление, затем провести сценарии раздела 14 ТЗ на двух Windows кассах и тестовой VPS базе.

Не применять `prisma migrate dev` к рабочей базе. Новые миграции развёртывать через `prisma migrate deploy` после резервной копии. Не переносить локальные `.env`, `.mvp-local` и тестовые данные на VPS.
