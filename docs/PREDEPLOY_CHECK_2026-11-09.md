# Проверка блокирующих проблем перед выкладкой — 09.11.2026

Production CRM не изменялась. В рабочей базе VPS уже есть товары, клиенты и остатки: начальная настройка должна сохранять эти данные. Сценарии сброса локального стенда к VPS неприменимы.

## Исправления

1. Общий фильтр `paymentMethodStoreFilter` применяется к списку способов оплаты и записи продажи (включая offline sync и завершение заказа), предоплате заказа, погашению долга и автоматическому выбору наличного метода возврата. Глобальные способы (`restrictedToStores=false`) сохраняют доступность; ограниченные требуют привязку к магазину операции.
2. Глобальный `FinancialFieldsInterceptor` убирает себестоимость, закупочные цены, прибыль, маржу и наценку из вложенных JSON ответов без соответствующих прав. `purchases.view` разрешает себестоимость; прибыль требует `finance.view`. Суммы продаж, цены продажи, даты и типы Decimal не искажаются. Фильтрация полей не заменяет проверку доступа к магазину/операции существующими guards.
3. Начальная настройка больше не сопоставляет магазины только по имени. Для существующего магазина приватный manifest требует `existingId`; сохраняются фактический ID, код и привязки остатков. Новый магазин создаётся только с явным `create: true`. Без сопоставления `--apply` останавливается до записей и создания файла паролей. Обычный запуск без `--apply` показывает реальные магазины, ID и количество связанных остатков/документов.
4. Применён переданный патч 15 кнопок заказов. Проверка общего UI: `issues: []`.

## Проверка

- Все 33 миграции применены на отдельной локальной БД `koreacrm_deploy_check_20261109`.
- API: typecheck, lint, 145 тестов, сборка.
- Web: typecheck, lint, 17 тестов, production-сборка с маршрутом заказов.
- Database: typecheck, lint; проверен синтаксис сценария настройки.
- `tools/verify-deploy-guards.mjs` выполняет реальные запросы к отдельной БД и поднимает временный HTTP API. Проверяет отказ чужих способов оплаты, разрешение своего, сохранность старых ID магазинов и остатков, отсутствие дублей после второго запуска, блокировку настройки без сопоставления и ответы консультанта/владельца с разными правами.
- Дополнительно выполняется `tools/verify-orders-real-db.mjs`: резервы, частичные оплаты, повторные запросы, завершение заказа, возврат и кассовые движения.

Проверочные данные создаются исключительно в БД с локальным адресом и именем `koreacrm_deploy_check_*`; скрипт отказывается работать с другим адресом/именем. Требуются предварительная сборка API, миграции и seed владельца `deploy-check-owner` в этой тестовой базе. Пароль передаётся через `SEED_OWNER_PASSWORD`, URL — через `DATABASE_URL`. Запуск из корня: `node tools/verify-deploy-guards.mjs`.

## Действия агента с доступом к VPS

1. Сделать резервную копию production базы и проверить архив. Не запускать локальные reset/verify сценарии на VPS.
2. Получить список реальных магазинов через dry run `db:provision` в окружении API контейнера. Приватный manifest передаётся через `KOREACRM_WORKSPACE_FILE`.
3. Вписать реальные ID Айни и Садбарга в `existingId` соответствующих записей. Не включать `create` для существующих точек. Проверить исходный перечень с владельцем, если связь неочевидна.
4. Убедиться, что `KOREACRM_IMPORT_LEGACY=0`; наличие старых товаров не означает, что их надо импортировать повторно. Не менять сохранённые пароли/права пользователей; несовпадения сценарий блокирует для отдельного разбора.
5. После публикации проверенного кода и миграций повторить dry run. Запускать `db:provision --apply` только с сопоставленным manifest и абсолютным новым путём `KOREACRM_CREDENTIALS_FILE` вне публичных файлов. Файл создаётся с правами 0600, не перезаписывается и содержит пароли только новых аккаунтов.
6. Проверить данные и повторный запуск на копии production перед применением к рабочей базе. Убедиться, что число товаров, клиентов и остатки не изменилось от начальной настройки.

Docker/Coolify сборка и восстановление production копии в этой сессии не проверялись. Публикация в main, запуск деплоя и запись начальных данных на VPS не выполнялись.
