## Online Windows POS

`apps/pos` now contains the first online Tauri POS. Set `VITE_API_URL` in `apps/pos/.env` to the API address, then run `corepack pnpm --filter @koreacrm/pos dev` for the UI or `corepack pnpm --filter @koreacrm/pos tauri dev` on a machine with Rust and Tauri prerequisites. Add the POS origin to `POS_ORIGIN` on the API. Apply migration `20261010150000_pos_devices` before using sales: devices must be registered to a store. On first login, select a store and connect the cash register. Registration is tied to that store; an owner can disable a device with `PATCH /stores/:storeId/pos-devices/:deviceId/status`.

The POS supports barcode scanners that type into the search field, cart quantities and line discounts, customer selection, mixed payments, cash shift opening and closing, sale creation and a nonfiscal receipt. Browser printing works from the receipt. Network ESC/POS printing uses a printer IP address on port 9100 and CP866 for Russian text. If the sale response is lost, the POS keeps the request locally and retries with its original operation ID.

The desktop POS keeps a local SQLite snapshot in its Tauri app data directory. After connecting a register, it refreshes the current store's products, barcodes, prices, available quantities, customers and permission list; the top bar shows the number of cached products and offers a manual refresh. Snapshots are separated by employee and store, and each refresh replaces the previous snapshot in one transaction. If the API becomes unavailable while the cashier remains signed in, product search, barcode lookup, price and stock lookup fall back to the local catalog. Local stock is reduced by queued sales and by sales synced since the last catalog snapshot. The browser preview still runs online.

Desktop checkout stores the exact sale request, including each item's unit price, in SQLite before sending it. A failed network request stays in a user and store scoped queue; the Sync Center shows pending operations and retries them every 30 seconds, when the network comes back, or on demand. Queued sales use `POST /stores/:storeId/sales/sync`, which preserves the operation ID and the checkout price, and accepts a negative stock balance if server stock changed while the POS was disconnected. A negative balance writes a `NEGATIVE_STOCK` audit event; a changed price writes an `OFFLINE_PRICE_DIFFERENCE` audit event. Normal online sales still use the current server price and reject insufficient stock. If the server has not yet gained the sync route, the POS falls back to the normal sales route. Other server validation errors are marked as conflicts for review. A queued operation is not a completed receipt until the server confirms it. Windows EXE tests have verified 20 queued sales after process restart, automatic delivery, unchanged stock on duplicate replay, and a sale synced at zero server stock. Offline login after reboot and a visible Notification Center remain separate work.

## Employees and roles

The Web cabinet has `/employees` for staff accounts and roles. Owners and authorized administrators can create or update employees, assign accessible stores and roles, reset passwords or PINs, and disable accounts. Each employee has a paginated action history from `GET /employees/:id/activity`; it shows actions performed by the employee and changes to their account without exposing audit payloads. Custom roles can be created and edited from the same screen; system roles are read-only. The API exposes `GET/POST/PATCH /employees` and `GET/POST/PATCH /roles` plus `GET /roles/permissions`. It enforces employee and settings permissions, prevents granting rights or stores beyond the actor's scope, hashes passwords and PINs, and audits changes. The local demo server includes a manager account (`manager` / `manager1234`) for checking role-limited navigation; production accounts use the database and Argon2 password hashes.

## Sales and customers API

The Web customer card at `/customers` shows an overview with purchase count, spend, average check, debt, contact details, birthday, address, personal discount, and the current bonus balance. Birthday, gender, address, and notes can be entered when creating or editing a customer. Automatic bonus earning remains disabled. The card also has paginated purchase, return, and debt history. `GET /customers/:id/history?kind=sales|returns|debts&page=1&limit=10` restricts transactions to stores assigned to the employee. Debt history omits the global running balance so staff cannot infer activity in other stores. The local preview includes a customer with a linked sale and two returns, plus another customer with a debt sale and partial repayment. The repayment form accepts sums and converts them to minor units for the API.

The customer card's Comments tab stores separate timestamped entries with the employee who wrote them. `GET /customers/:id/comments?page=1&limit=10` requires `customers.view`; `POST /customers/:id/comments` requires `customers.edit` and accepts `{ "text": "..." }` up to 2000 characters. Each creation is audited without copying the comment text to the audit log. Apply migration `20261013160000_customer_comments` before using this feature with the real API. The local demo server includes a sample comment and supports adding new ones.

The History tab combines purchases, returns, debt repayments, comments, bonus operations, and customer profile changes in a dated timeline. `GET /customers/:id/activity?page=1&limit=10` paginates this timeline and limits store transactions to the employee's assigned stores. The demo preview is available at `http://127.0.0.1:3004/customers` with `demo` / `demo1234`.

Customer segments are derived from current purchase statistics. The card shows matching segments and their rules; the customer list can filter by segment with `GET /customers?segment=NEW|REGULAR|VIP|DORMANT|HIGH_CHECK|FREQUENT`. `GET /customers/:id/segments` returns the card badges. MVP thresholds are: new up to one purchase, regular from three, VIP from five and 5,000,000 UZS spent, dormant after 90 days without a purchase, high average check from 500,000 UZS, frequent from three purchases within 30 days. Segment values are recalculated when the list or card is loaded.
Run `node tools/seed-web-customer-segments-preview.mjs` against the demo server to add Elena with three purchases for the regular and frequent segment preview.

The customer card's Bonuses tab displays the bonus ledger and current balance. An employee with `settings.edit` can add or subtract a manual correction with a required reason; the API refuses negative balances and treats a repeated `operationId` as the same operation. `GET /customers/:id/bonuses` requires `customers.view`, and `POST /customers/:id/bonuses/corrections` requires `settings.edit`. Apply migrations `20261013170000_bonus_transactions` and `20261013180000_enable_bonus_payments` before using bonus payments with the real API. Automatic bonus earning remains disabled.

Online Web checkout and the browser POS preview can split a sale between bonuses and another payment method. A customer is required, and the bonus amount cannot exceed the current balance. The API creates a `SPEND` ledger entry and reduces the balance in the same serializable transaction as the sale; replaying the sale operation does not spend bonuses twice. The Windows desktop POS omits bonus payments because its offline queue cannot verify the live balance. The demo customer Anna starts with 150,00 bonus units for preview.

The customer card also edits `discountPercent`. POS applies the selected customer's percentage to each line after its manual discount, rounds down to minor units per line, shows the discounted total before payment, and sends the combined line discounts in the sale request. The local customer cache stores the percentage for offline checkout and migrates existing cache files with a default of zero. The demo customer Maria has a 10% discount for preview.

The POS also accepts a fixed or percentage discount for the whole receipt. It applies this after line and customer discounts, distributes the amount across sale items in minor currency units, and sends the final line discounts to the API. The receipt and any partial cash return use those discounted line totals. A receipt discount greater than the remaining total blocks checkout.

Web checkout at `/sales` now applies the same order of discounts: manual item discount, selected customer's personal percentage, then a fixed or percentage discount for the whole receipt. It shows each final item amount and rejects a discount above the remaining total. Item quantity is automatically limited to the available stock with an explanation. The live web preview is `http://127.0.0.1:3004/sales` with `demo` / `demo1234`.

Web checkout and POS monetary fields accept ordinary sums, for example `150`, `150,50` or `150.50` for 150.50 UZS. This includes fixed discounts, payments, and cash shift amounts. The fields display two decimal places after leaving them; percentages remain percentages. Input is converted exactly to integer minor currency units for calculations and API requests. More than two fractional digits are rejected.

The Web `/finance` screen also accepts and displays ordinary sums for expenses, supplier payments, cash shift opening and closing, and signed cash corrections. It converts entered sums to exact minor units for the API. The local demo server serves the finance summary, expense categories, expenses, and cash shift operations so these flows can be reviewed at `http://127.0.0.1:3004/finance`. Demo profit and cost are shown as unavailable because the demo server has no batch costs; supplier payment examples require the real API and purchases.

The Web dashboard keeps two decimal places in financial metrics and displays unavailable profit metrics as a dash. Employees with `inventory.view` see a live low-stock panel across their accessible stores. Each item links to `/stock` with the matching store and low-stock filter selected; low stock means quantity is at or below that store's configured minimum.

The Web `/stock` product card has a separate write-off form for damaged or expired goods. Enter a positive quantity and a reason; `POST /stores/:storeId/stock/write-offs` requires `inventory.adjust` and a UUID `operationId`. The server checks unreserved stock inside a serializable transaction, records a `WRITE_OFF` movement and audit event, and returns the existing movement on a matching retry. A reused operation ID with different details is rejected. The demo server supports the same preview flow.

The Web application has `/customers` for customer search, creation, editing and debt repayment, and `/sales` for online checkout, mixed payments, cash shift opening, printable receipts, and searchable sale and return histories. In a cash sale's details, an authorized employee can return selected quantities, give a reason, and open a cash shift for the current browser device when needed. The return history is available through `GET /stores/:storeId/sales/returns`, ordered by return date, with receipt, reason and returned items. The sale form uses the latest store price and available stock shown by the API; the server checks both again when completing the sale.

`/customers` supports search, creation, updates and soft deletion. `GET/POST /stores/:storeId/customers/:customerId/payments` lists and records debt repayments. `/sale-payment-methods` lists and configures sale payment methods. `GET/POST /stores/:storeId/sales` lists and completes sales; `GET /stores/:storeId/sales/:id` returns a receipt snapshot. A sale request needs a UUID `operationId`, `deviceId`, item quantities and payment amounts in minor currency units. Cash payments also need an open `cashShiftId` for the same device. Mixed payments, customer debt, and online bonus payments are supported; voids are pending. Sales reserve no stock and require an active store price, available stock and a received purchase batch for cost. The sale, stock movements, cash posting, customer balance and audit log commit together. Repeating the same `operationId` returns the existing sale. `POST /stores/:storeId/sales/:id/return` performs a full or partial return of a cash-paid sale with an open shift and enough cash; it requires a UUID `operationId`, `deviceId`, `cashShiftId`, reason, and optional `items: [{ saleItemId, quantity }]` for partial returns. The original sale stays in history, and each return restores the selected stock, withdraws cash and reduces revenue on the return date. Repeating the same return operation does not repeat these effects.

Apply migration `20261010070000_sales_customers` and rerun the database seed before using these routes. The current finance summary includes sale revenue, cost and gross profit; its `cashFlowMinor` remains unavailable until complete cash flow accounting is implemented. Store scoped reports omit the global customer debt balance.

## Требования

Node.js 22+, pnpm 10, Docker Compose. Для сборки desktop POS также нужен Rust и системные зависимости Tauri.

## Локальный запуск

1. Скопируйте `.env.example` в `.env` и смените пароли при работе вне локальной машины.
2. `corepack enable` и `corepack pnpm install`.
3. `docker compose up -d`.
4. Задайте `JWT_SECRET`, `SEED_OWNER_LOGIN` и `SEED_OWNER_PASSWORD` в `.env`.
5. `corepack pnpm --filter @koreacrm/database db:migrate`.
6. `corepack pnpm --filter @koreacrm/database db:generate`.
7. `corepack pnpm --filter @koreacrm/database db:seed`.
8. `corepack pnpm dev`.

Web: http://localhost:3000, API: http://localhost:3001/health, Swagger: http://localhost:3001/docs, MinIO: http://localhost:9001.

Авторизация API: `POST /auth/login` с `login`, `password`, необязательным `deviceId`; `POST /auth/refresh` и `POST /auth/logout` с `refreshToken`; `GET /auth/me` с Bearer access token. Refresh token хранится на клиенте безопасно и заменяется при каждом обновлении. Для POS следует передавать стабильный `deviceId` при входе и обновлении.

Каталог API: `/brands`, `/categories`, `/products` поддерживают список, создание, просмотр, изменение и мягкое удаление. Список товаров принимает `page`, `limit`, `search`, `sku`, `barcode`, `brandId`, `categoryId`, `status`. Точный поиск доступен также по `/products/lookup/sku/:sku` и `/products/lookup/barcode/:barcode`. Настройки товара для магазина: `GET` и `PATCH /stores/:storeId/products/:productId/settings`.

Остатки: `GET /stores` возвращает доступные пользователю магазины; `GET /stores/:storeId/stock` принимает `page`, `limit`, `search`, `filter=all|low|negative|zero`, `brandId`, `categoryId`; `GET /stores/:storeId/stock/movements` возвращает историю. Ручная операция `POST /stores/:storeId/stock/adjustments` принимает `productId`, `type=CORRECTION|INVENTORY`, signed `delta` и обязательный `comment`. Сервер записывает движение, остаток и аудит в одной транзакции. Для будущих продаж и закупок `StockService.applyMovement` принимает устойчивые `sourceType` и `sourceId` и обеспечивает повторное применение без удвоения остатка.

Проверки: `corepack pnpm lint`, `corepack pnpm typecheck`, `corepack pnpm test`, `corepack pnpm build`.

Текущий этап содержит инфраструктуру, авторизацию, каталог, склад, финансы и продажи. Web-экраны доступны по `/products`, `/brands`, `/categories`, `/stock`, `/inventories`, `/transfers`, `/suppliers`, `/purchases`, `/finance`. Настольная касса хранит каталог и очередь продаж в SQLite. После успешного входа и регистрации устройства она сохраняет локальный проверочный хеш пароля на семь дней: при недоступном API кассир может войти после перезапуска, работать с локальным каталогом и сохранять продажи в очередь. При восстановлении связи касса повторно авторизуется, проверяет права и отправляет очередь. Ожидаемая сумма кассовой смены учитывает наличные продажи в локальной очереди, а после синхронизации обновляется по данным сервера. Пока есть неотправленные наличные продажи, закрыть смену нельзя. Открывать и закрывать смену без связи нельзя; для наличной продажи нужна смена, открытая до отключения. Браузерная демоверсия требует работающий демо-сервер и не использует SQLite.

Если сервер отклонил сохранённую продажу, Центр синхронизации показывает причину, сумму, время, оплату и номер операции. Такая продажа не повторяется автоматически. После исправления причины кассир может вручную повторить отправку с тем же номером операции; исходный чек в SQLite сохраняется. Текущий чек после отказа очищается, чтобы не оформить ту же продажу дважды.

История чеков в POS доступна после подключения к серверу: поиск по номеру чека или телефону клиента, просмотр товаров, оплаты и статуса, повторный показ нефискального чека для печати. Поиск ограничен текущим магазином. Из истории можно оформить полный или частичный возврат наличной продажи, указав количество каждой позиции, при открытой смене и достаточной сумме в кассе. Возврат работает при подключении к серверу; безналичные возвраты пока не поддерживаются.

Поставщики: `/suppliers` поддерживает список, создание, редактирование и мягкое удаление. Закупки: `/stores/:storeId/purchases` поддерживает черновик с позициями, изменение черновика, отправку заказа, отмену и частичную приёмку через `POST /:id/receivings`. Приёмка принимает `operationId` (UUID) для безопасного повтора запроса и массив позиций с номером партии. Партия, движение товара, остаток, принятое количество и долг поставщику записываются в одной транзакции. Денежные значения передаются строками в минимальных единицах валюты.

Инвентаризация: `/stores/:storeId/inventories` позволяет создать черновик, начать подсчёт с фиксацией ожидаемых остатков, задать фактическое количество вручную или увеличить его по штрихкоду, завершить либо отменить подсчёт. Завершение требует `countUncountedAsZero: true`: товары без фактического подсчёта считаются нулевыми. Если остатки изменились после начала инвентаризации, завершение отклоняется. Все корректировки остатков и движения записываются в одной транзакции. Web-экран: `/inventories`.

Перемещения: `/transfers` поддерживает создание и изменение черновика, заявку, согласование, отправку, частичную приёмку и отмену до отправки. Отправка списывает доступный остаток в исходном магазине; приёмка добавляет фактически полученное количество в целевом. Приёмка использует `operationId` (UUID) для безопасного повтора. Каждая операция меняет остатки, движения, статус и аудит в одной транзакции. Сотрудник исходного магазина управляет заявкой и отправкой; сотрудник целевого магазина принимает товар. Web-экран: `/transfers`.

Финансы: `/expense-categories` поддерживает редактируемые категории; `/stores/:storeId/finance` — расходы, кассовые смены и операции, оплаты поставщикам. Наличные расходы и выплаты из кассы уменьшают ожидаемый остаток смены в той же транзакции. Оплаты поставщикам уменьшают долг закупки и общий баланс поставщика. `GET /finance/summary?from=YYYY-MM-DD&to=YYYY-MM-DD&storeId=...` возвращает расходы, движение кассы, долг поставщикам, оплаты и открытую наличность. Периоды отчёта считаются по UTC. Денежные значения передаются строками в минимальных единицах валюты. Выручка, себестоимость и прибыль рассчитываются по завершённым продажам. Полный денежный поток пока возвращается как `null`; долг покупателей доступен только для сводки по всем магазинам. Web-экраны: `/finance`, `/finance/categories`.
